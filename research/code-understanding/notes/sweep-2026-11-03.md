## Findings

### A. RepoProbe — checklist scoring for architecture questions
- **What:** 500 GitHub Discussions question-and-answer pairs from 50 repositories (15 languages). The Checklist-Based
  Verification Protocol scores an open answer as atomic items. Each item has a key point, a score weight, and a
  discrete rubric. Knowledge items (1 to 4 of them) have integer weights that sum to 9 on a 10-point scale. The last
  point is clarity and organization. The judge writes a rationale first, then picks a score from the rubric's allowed
  values. The paper reports that this is more stable than scalar LLM-as-a-Judge (standard deviations roughly half, in
  the reliability table). In the aggregate results table, every model's clarity score is higher than its knowledge
  score. One row: GPT-5.2, knowledge 60.3, clarity 84.7. The paper's line is that clarity consistently outpaces
  technical correctness. Edit Bias means the model proposes code or config instead of accounting for the architecture
  that is already there. Among answers scoring below 60%, that mode is 10.4% (GPT-5.2), 13.0% (the table's Claude
  column), 24.0% (the table's Gemini column), and 15.8% on average. A separate judge (Gemini 3 Flash) assigned the
  categories. The authors say they manually inspected the Edit Bias cases.
- **Source:** [arXiv 2608.04783](https://arxiv.org/abs/2608.04783) (HTML v2, 6 Aug 2026).
- **Evidence:** `measured-obs` (a paper evaluation of models, not a study of human reviewers).
- **Use:** supporting evidence and a test method for BACKLOG #1 and #3. Keep the multiple-choice quiz. Add 1–2
  open-ended architecture questions, each fact tied to a `path:line`, scored with a checklist rather than one scalar
  judge score. Not a new ranked item. The same protocol is how #3's lessons should be scored. Edit Bias is a caution
  about the model that writes the page: it may emit a config or a patch when the question was about structure.

### B. Cabra — for agents, understanding predicts errors better than edit size
- **What:** Cabra (Coding Ability Blueprint for Rigorous Agent evaluation), Microsoft Research (Nishant Balepur,
  Kiran Tomlinson, Tobias Schnabel). Eight LLMs and six coding agents on 6,840 synthetic tasks. On released
  mini-swe-agent traces for SWE-bench Verified (Claude-4.5 Opus and Sonnet, Gemini-3 Pro and Flash, GPT-5.2, GPT-5
  Mini), the point-biserial correlation of each metric with agent accuracy is low. The count of understanding tool
  calls, defined as Read plus Analyze, correlates more strongly than edit-token use or lines edited. The paper does
  not print the coefficient in prose. A second task asks the agent to move shared logic from two classes into a
  parent class and leave the differences behind. As lines per class grow through 5, 10, 25, 50, 100, and 200 (50
  tasks at each size), agent accuracy drops and Understand calls rise, while the edit itself stays modest (on the
  order of the line count). Agents keep behavior in over 90% of cases. Most failures are leaving too many lines in
  the child class. The ethics statement cites (Im)Paired Programming
  ([arXiv 2607.26375](https://arxiv.org/abs/2607.26375)), already in draft 3, as evidence that programmers struggle
  to understand code when they work with agents. That citation is not one of Cabra's experimental results.
- **Sources:** [arXiv 2610.10610](https://arxiv.org/abs/2610.10610),
  [code](https://github.com/microsoft/CABRA). X mention
  ([post](https://x.com/atpulsehq/status/2116187883958677661), 2026-10-30): `public_metrics` bookmark_count 0,
  impression_count 0, like_count 0, quote_count 0, reply_count 1, repost_count 0. The post's wording is stronger
  than the paper's ("fail mainly when the code is hard to understand").
- **Evidence:** `measured-obs` for the paper. `engagement` for the post. This measures **agent** understanding, not
  a person's.
- **Use:** supporting evidence for #1 and #2. A metric that only counts edits, or only time until approval, can miss
  a failure of understanding. No new agent-eval skill.

### C. PR Explainer — a narrated tour, plus a repo that narrates itself
- **What:** PR Explainer (prexplainer.com) plays a voice over a change while the lines it is talking about light up.
  Depth is brief, standard, or detailed. Export is an MP4 with captions, a PDF, or a `.prtour` file that reopens
  against a checkout. The same product shows severity-graded findings (critical, warning, good practice) in the
  gutter. A background daemon, Code Stories, narrates the repo over time: a timeline, pinned milestones, and a local
  pulse, for onboarding and for "what changed last week." The page's sample chronicle is product copy, not a repo
  we checked. Separately, Bisque posts a short video on a pull request from a Claude Code run, and skips changes it
  judges too small to walk through.

### D. Saga and Guided Review — peers of the page we already ship
- **What:** Saga is a CLI. It diffs the branch, asks a model to group the change into ordered chapters, and writes
  one self-contained HTML file. Line and file comments can be pushed to a pending GitHub review (`saga comments
  push`). Install is `uv tool install saga-cli`. Bring your own key. Guided Review parses the real unified diff
  into files, hunks, and lines, then walks ordered units (schema, then logic, call sites, and tests) in a Chrome
  extension or a local CLI. The docs say the model plans structure and commentary only, and never invents the code
  lines. Without a key the walk is file by file. Apache-2.0.
- **Sources:** [Saga post, 2026-07-13](https://jakeberesford.com/blog/saga),
  [repo](https://github.com/JakeBeresford/saga). GitHub API at 2026-11-03T13:22:10Z: 20 stars, created
  2026-07-11T19:32:42Z. [Guided Review docs](https://guidedreview.dev/docs).
- **Evidence:** `practitioner` for the Saga post. `vendor` for Guided Review's docs.
- **Use:** named in the Shipped notes for the HTML page and for reading order. Same job human-review already does.
  Not ranked.

### G. aictrl — teach the change, then count which claims are tied to code
- **What:** An explanation is a different artifact from a review. The teaching text (what it does and why, terms,
  diagrams) comes first. Reviewer notes (reading order, files to open, what to probe) are last and collapsed. That
  order is what human-review already does by holding findings back. The parts that are not already shipped: a
  footer, "N claims grounded · M ungrounded"; every diagram step opens the file and lines, with the code at the
  explained commit and what this pull request changed there; badges for "New in this PR" or "Changed in this PR";
  Trace and Walk on an ending; and the diagram type chosen from signs in the code (states, overlapping work,
  messages between parties, a decision, a schema change), recorded on one `Diagram choice:` line. A lint fails the
  run when a "yes" has no diagram of that type. File references are pinned to the explained commit.
- **Sources:** [blog, 22 October 2026](https://aictrl.dev/blog/understand-a-pull-request-before-you-review-it),
  [docs](https://aictrl.dev/docs/pr-explanations).
- **Evidence:** `vendor`.
- **Use:** one new ranked item, #10. Cost S–M, target HR, proposed. The teaching-before-findings order is not
  re-ranked, because it is shipped. The item is the footer, the step-to-`path:line` map, and the diagram-type
  line.

### H. diff-tour — ask, then reveal
- **What:** Coverage of an open-source CLI, diff-tour, by Dai Aoki. It turns a branch or pull-request diff into
  steps. It asks a review question (what if this runs twice, can the migration roll back, would tests fail, is
  this blocking) before it shows the explanation. The article says the code on screen is read from git at the
  commit, not copied out of the model's prose, and that the tool is local and read-only. No Product Hunt page was
  opened, and the article gives no upvote count and no repository URL.
- **Source:** [AIToolly, byline 29 October 2026](https://aitoolly.com/ai-news/article/2026-11-03-diff-tour-launches-on-product-hunt-helping-developers-read-ai-code-like-senior-engineers).
  The URL path is dated 2026-11-03.
- **Evidence:** `vendor` (launch coverage).
- **Use:** folded into #1. The multiple-choice block stays. At one or two reading-order stops, withhold that
  stop's annotation until the reader answers one or two probe questions, then reveal it. Cost of that slice S–M.
  Not a new item.

### I. Scrimba — four beats, and a warning about video
- **What:** Per Harald Borgen, 10 September 2026, walks one merged Vite pull request (#23387) in four beats, in
  order: what changed, why, which runtime flow it touches, and what it deliberately does not address. The guide
  says the fourth beat is the one that gets cut, and that a change described only by what it fixes cannot be built
  on safely. It also says a video walkthrough is a poor place to keep reference: it cannot be grepped, it does not
  change when the code does, and a link can point at a timestamp but not at a sentence.
- **Source:** [Scrimba](https://scrimba.com/articles/how-to-explain-a-pull-request-to-your-team-2026/).
- **Evidence:** `practitioner`. The later section that sells Scrimba Explain is `vendor` and is not used as a
  ranked source.
- **Use:** a note on the diverse-explanations item (draft 3's #12, draft 4's #13). Add the non-goals beat as one
  short line, not as a new item. The video warning is noted on the narrated modality (#14).

### J. Two families of diagrams — a drawing is not a blast radius
- **What:** Raghav Chamadiya, who builds repowise (the post says so), updated 1 November 2026. One family asks a
  model to draw a story. The other parses imports into a graph. On Flask, the post says a GitDiagram drawing
  showed 15 of 24 Python modules under `src/flask` and left out `globals.py` (imported by 12 modules) and
  `helpers.py` (imported by 9). The author's parse found 78 runtime import edges. A box with no arrows can mean
  the file is unused, or that the model never sampled it. The post's rule: use the drawing to learn the story, and
  the parsed graph to decide what a change will break. Do not read a missing box as "unused."
- **Source:** [repowise guide](https://repowise.dev/blog/guides/generate-architecture-diagram-from-github-repo).
- **Evidence:** `vendor`. The author is a party to the comparison. One repo, checked by that author.
- **Use:** folded into #7, and into the shipped honesty note. It is the same split Floorplan already argues
  (scripts for structure, the model for names). Not a new item.

### K. Hand off — review quality only
- **Qodo's Codex plugin** (OpenAI, 2 November 2026). The page says the plugin brings organizational context,
  codebase rules, and an independent review into a Codex session, including across repositories, and returns
  findings before a pull request is opened. That is review quality.
  [Post](https://openai.com/index/qodo-codex-plugin/).
- **PR Explainer's findings half.** Severity-graded comments in the editor. The narrated tour stays in #14.
- **CodeRabbit's explainability guide** (Brandon Gubitosa, 13 August 2026). A reviewer's sequence: check intent
  against the diff, read a walkthrough, trace blast radius, then read adversarially. The guide cites a 470-PR
  report for higher issue rates in AI-authored pull requests (10.83 issues per PR versus 6.45, readability more
  than 3×, logic and correctness 75% more common, error-handling nearly 2×, security up to 2.74×). Those figures
  are the guide's. They were not re-measured here. The piece is about finding defects, so it is handed off even
  where a walkthrough or a blast radius overlaps this backlog.
  [Guide](https://www.coderabbit.ai/guides/code-explainability-for-ai-generated-prs-a-reviewers-guide).
