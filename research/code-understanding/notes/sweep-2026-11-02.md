## Findings

### A. (Im)Paired Programming — agents help completion and harm comprehension
- **What:** 54 students each built a website with one of two systems: an editing agent, or a chatbot where they wrote
  the code themselves or adapted generic snippets. Understanding was tested with comprehension questions and a task
  that extends the code without the agent. Agents aided the initial completion. They harmed code comprehension, so
  users were not prepared to extend their code. Low-effort interaction types (copy+paste prompts, auto-accepted
  edits) were linked with lower comprehension. Users reported weaker understanding and still preferred agents,
  because they are quick and easy to use.
- **Sources:** [arXiv 2607.26375](https://arxiv.org/abs/2607.26375),
  [code](https://github.com/nbalepur/impaired-programming).
- **Evidence:** `measured-RCT` (student sample).
- **Use:** supporting evidence for BACKLOG #1 (quiz) and #2 (measure it). #2's test adds an "extend it without the
  agent" task beside the quiz: a small follow-up change made by hand after reading the page. The same task is in
  #3's test.

### B. TARS — adapting explanation depth saved time and did not raise correctness
- **What:** an in-IDE (VS Code) agent that profiles a developer's expertise, role, and stylistic preferences and
  adapts the depth and tone of explanations anchored to the code. Within-subjects, n=18, on non-trivial Java
  snippets (two with TARS, two without, counterbalanced). Completion time was 26% lower (mean 224.0s vs 304.08s).
  A Mann-Whitney U test did not reach significance (U=494.5, p=0.085). Correctness, measured as cosine similarity
  to a ground-truth docstring, did not differ (0.888 vs 0.886; t(16)=-1.52, p=0.18). The abstract says participants
  reported lower cognitive load. In the results, NASA-TLX mental demand, effort, and frustration sit significantly
  below the neutral midpoint, and Table II is the TARS condition only. The introduction also says workload was lower
  than the manual condition; that contrast is not the test reported in the results.
- **Source:** [arXiv 2607.15948](https://arxiv.org/html/2607.15948v1).
- **Evidence:** `measured-RCT` (small, null on correctness).
- **Use:** caution on BACKLOG #8 (two-depth background). Adapting depth may save time. It has not been shown to
  improve understanding. #8 stays cost S, and quiz score stays the guard.

### C. Diverse LLM explanations — a small open-ended gain that did not survive correction
- **What:** 971 first-year computing students, randomized between subjects to three diverse LLM explanations or three
  generic ones, on two programming exercises. Diverse explanations each emphasize a different aspect (the paper's
  examples are function, concept, and goal). Open-ended accuracy was about 7.7% higher with diverse explanations
  (sumArray +7.74, randomizeString +8.10, countChar +7.70). Logistic regression with a Bonferroni adjustment: the
  condition effect was not significant (z=2.15, p=0.095). Multiple-choice accuracy was high in every condition
  (>87%) and did not differ (chi-square p>.05). The abstract reports no difference in perceived cognitive load.
  785 of 971 students had open-ended responses complete enough to score; all 971 completed the multiple-choice items.
- **Source:** [arXiv 2606.28882](https://arxiv.org/abs/2606.28882).
- **Evidence:** `measured-RCT` (education, weak).
- **Use:** new BACKLOG item, ranked below "Who to ask": explain the core change from two or three angles (what it
  does, which concept it relies on, why it exists). Cost S, target HR + #3, status proposed. Test: alternate PRs
  with and without the extra angles and compare quiz score.

### D. Floorplan — a plain-English map, scanned by scripts and named by the model
- **What:** a Claude Code and Codex plugin. Dependency-free Node scripts scan files, imports, routes, and web
  requests, and match each frontend request to the backend endpoint that answers it, including across repos. The
  model names the parts in plain English. Output is a local `floorplan/index.html`. The `floorplan/` folder ignores
  itself in git. The map zooms from the app to a part, a file, and an endpoint. "Start from a screen" opens
  everything behind a page the reader knows. The Ask bar returns an answer, a mini-map of the pieces involved, and
  a step-by-step walkthrough. "Update the floorplan" re-reads only what changed and highlights Recent work. Names
  edited in `floorplan/architecture.json` are kept on later updates.
- **Sources:** [repo](https://github.com/haydenschmitty/floorplan). GitHub API on 2026-11-02: 2,069 stars, created
  2026-10-27. Current release v0.6.1 (published 2026-11-01); v0.6.0 was published 2026-10-31. X mention
  ([post](https://x.com/ai_algoit/status/2116825143930732789): 0 likes).
- **Evidence:** `vendor` + `engagement` (stars).
- **Use:** (1) added to #3's sources as the strongest new map-style baseline, and as a second baseline arm in #3's
  v2 test, beside DeepWiki. (2) added to #7: deterministic scan for structure, model only for naming;
  request-to-endpoint matching is a cross-boundary edge that HR's grep does not see. (3) "Start from a screen or
  endpoint the reader already knows" is folded into #3. It is the lesson's opening move (begin at a surface the
  reader can already name, then the stops go behind it), so it stays inside that skill. It is not a separate ranked
  item.

### E. DiffNotes — the agent that wrote the PR explains it, off to the side
- **What:** an agent skill, or an MCP endpoint. The agent that wrote the PR uploads a summary, a deploy card
  (migrations, flags, rollback), a risk list, and one note per changed block explaining why, not what. A browser extension draws the notes on GitHub's Files changed tab. Nothing is posted to the PR. Notes
  expire. A `.diffnotes.yml` on the base branch holds per-repo rules the agent reads before writing. The post's
  example is "every migration needs a deploy note".
- **Sources:** [DEV, posted 2026-11-01](https://dev.to/igorkasyanchuk/i-made-my-coding-agent-explain-its-own-pull-requests-j67),
  [repo](https://github.com/igorkasyanchuk/diffnotes). GitHub API on 2026-11-02: 3 stars.
- **Evidence:** `practitioner` (low engagement).
- **Use:** (1) added to #5. The post's premise is the same one: the agent knows why, and the reviewer does not.
  (2) new item "Per-repo explanation rules file": repo-owned rules the page must satisfy (a migration gets a
  deploy note and a rollback note). `build --check` fails when a required note is missing. That failure is our
  check; DiffNotes describes the agent reading the rules before it writes. Cost S, target HR, status proposed.
  Test: limitless PRs that touch migrations or config. Ranked #9, under the always-on short items (#6 Ask, #7
  blast radius, #8 two-depth) and above the split advisor. The check is cheap because `build --check` already
  exists, and it only fires when a rule matches, on thin evidence.

### G. Hand off — trust in explained code review
- **What:** "Evaluating the Impact of Explainable AI on Trust in AI-Assisted Code Review." Within-subjects, n=34,
  three explanation levels. Full explanations gave the highest perceived trust (M=3.99/5) and did not give the
  highest agreement. Moderate explanations gave the highest agreement with the AI recommendation (89.22%). No
  explanations were lowest on trust and on agreement. Explanation level did not significantly affect review time.
- **Source:** [arXiv 2607.24601](https://arxiv.org/abs/2607.24601).
- **Evidence:** `measured-RCT`.
- **Use:** added to "Hand off to Code Review Research Bot." It measures trust and agreement with an AI review, which
  is review quality, outside this backlog's ranking.
